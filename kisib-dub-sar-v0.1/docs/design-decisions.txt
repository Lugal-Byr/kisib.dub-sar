kisib.dub-sar — design decisions and retained functions
Recorded: 2026-10-06, America/Los_Angeles
Status: functional requirements recorded; visual direction awaiting selection.

This journal preserves the decisions that drive the interface. A new visual
option does not remove a function. Changes to a function must name the stable
function ID in function-catalog.csv and record the replacement decision here.
The catalog distinguishes prepared source, planned functions, and retained
wishlist items. Documented means API documentation exists, not that the app
has passed a Windows test. The source register retains the original feature identities and explicitly records later logging corrections and additions.

D001 — Classic window
Win95 Explorer appearance. Permanent branching tree on the far left, results
on the right, details below. Native grey controls, square corners, dotted tree
lines, plus/minus boxes, plain menus, sortable lists and resizable dividers.
No backup or import controls are part of the current explorer.

D002 — Enumeration gate
v0.1 remains read-only. Open and account for the actual Windows 11 Home/Pro
store inventory first. Store writes, blocking enforcement, chain construction,
country/owner data ingestion, and software-use tracing require later gates.
The generated pictures depict proposed views with sample data. Their chains,
policy states and counts are illustrative, not observations from the PC.

D003 — Issuer organizing controls belong on the far left
Put Issuer explorer, Find issuer, Group by and Sort by above the Explorer tree.
These controls drive the selected branches and all right-hand views. Issuer
organization must not move into a separate dashboard on the right.
Browsing modes retain Windows stores, issuer/CA owner, country and custom tag
views. The real store view preserves location > system store > physical store.
Virtual groups do not become fake registry paths.

D004 — Search, group and sort
Planned search covers complete subject/issuer strings, mapped CA owner,
country name/code, tag and full certificate/SPKI hashes. Show matching evidence
and unresolved mappings. Sorting is chosen on the left: issuer/owner name,
country name/code, tag, observed store, policy state or expiry; ascending and
descending where meaningful. Sort siblings without changing chain order or
breaking the native location/system/physical hierarchy.
One selected tree branch drives a sortable certificate grid, owner standings,
the future playoff chain view, and the lower Details / Issuer 🏛️ pane.

D005 — Enabled and Blocked within each group
Each category, including 👑 Monarchy, has Enabled and Blocked sibling branches.
Unresolved effective status stays Unknown/Not evaluated in the result fields.
Record requested user policy separately from observed Windows trust, its store
scope, user/machine identity, application verifier, purpose, time and evidence.
A picture's Enabled/Blocked label is a proposed policy state, not proof that
Windows or every application enforces it. No writes or enforcement are added
to the read-only source while the machine gate is open.

D006 — Persistent blocking requirement
The goal is a retained blocking rule that survives a certificate returning
through an update or another store source. Deleting a certificate is not the
specified policy mechanism. Compare explicit Windows distrust, trusted roots,
CTL membership, group policy and application-specific trust stores. Report
unsupported scopes and conflicts; do not claim universal enforcement.
Persistent policy storage, reconciliation and before/after application checks
are future work, not implemented certificate-store changes.
Proposed conflict rule: a matching block takes precedence within the same
declared scope. This is a design proposal to test, not a Windows rule.

D007 — Several categories on one issuer/certificate
Categories are independent labels. Russia receives 🌿, 🧱 and 🇷🇺, displayed
together as 🌿🧱🇷🇺, while remaining browsable in three separate groups.
The requested BRIC/BRICS mapping assigns both 🌿 and 🧱; each is an independent
tag, not a single combined category. Keep original BRIC and current BRICS
membership fields separate until the user chooses which membership set drives
the rule. Monarchy-country mappings assign 👑. Additional 🏛️, 💀 and 💃 groups
are retained; meanings not supplied by the user stay undefined and editable.
🌿 is user-defined; it must not be represented as documented Basel/BIS
membership or proof of political control. One DER identity retains every
observed store occurrence and every applicable tag; virtual views share it.

D008 — Country directory and automatic labels
Prepare a country/area reference with full name, ISO alpha-2, ISO alpha-3 and
source date. Distinguish sovereign countries from territories/other areas.
Include a sourced monarchy classification, original BRIC membership, current
BRICS membership/status/source/date, editable user labels and separate notes.
Unknown or disputed classifications remain visible. This reference is planned;
no complete monarchy/BRICS classification table has been published in v0.1.
The official country-code reference is UNSD M49:
https://unstats.un.org/unsd/methodology/m49/

D009 — Country and ownership evidence
Show subject C=, recorded issuer C= and sourced CA owner country separately.
Choose and record the country field that drives each automatic grouping rule.
An issuer C= in an unvalidated certificate is a recorded claim. Country,
monarchy or BRICS tags are not proof of who controls a CA, a traffic route,
certificate misuse, a signing instruction or an application's current use.
Owner matching needs a sourced certificate/issuer mapping, not an assumed
equivalence between a display name and a company or government.

D010 — Playoff branch/grid
Selecting an issuer/group can show an NFL-playoff-style view on the right.
Certificate links come from CertGetCertificateChain return data after its gate.
Retain every returned simple chain/context, incomplete endpoints and observed
issuer-store evidence. Preserve the already specified SHA-1/SHA-256/SPKI
metadata and signal rules. Hashes are lookup keys, not parent links.
The rightmost software-scope area separates policy, trust evaluation and actual
observed use. Inventory presence alone never becomes an Active-use event.

D011 — History log button and stacked scopes
Keep a visible History log button next to the grid/details. Scope it to a
certificate, issuer/CA owner, selected category or software process. Permit
switching between present and previous snapshots and dated rule versions.
Preserve event time, snapshot/event ID, certificate identities, physical/logical
store paths, rule ID/version, requested policy, observed result, verifier scope
and the application's identity when genuinely observed. Unknown remains unknown.
Scoped views reference the same events and deduplicate by event ID. They do not
invent several separate copies of history. Retain labels as they were recorded
at the event, with a clearly separate optional current-label view.
Existing v0.1 logs contain this application's read actions and errors. They are
not OS-wide software usage logs. Reading existing CAPI2 diagnostics is a future
evidence source; disabled logs, gaps and unsupported crypto stacks stay visible.

planned function; do not claim all programs share the Windows stores.

D021 — Original app evidence comes before interpretation
Read available Windows CAPI2 Operational records with EventLogWatcher, retain
original XML and source fields, then advance a replay bookmark after durable
commit. System.Execution is the emitter; it is not automatically the broker's
client. Process ID plus an observed start time identifies a lifetime. Missing
identity, unparsed payloads, denied logs, unsupported verifiers and source/log
loss remain explicit. Certificate references are hash lookup candidates, not
parent links. Syscall enter/exit addresses and NTSTATUS are separate evidence;
do not guess a certificate purpose, symbol name or paired operation.

D023 — Owned ETW capture, full ETL, explicit coverage limits
Optional syscall capture creates a unique dedicated System Logger session,
using documented ETW APIs; it never takes ownership of NT Kernel Logger or
stops someone else's session. It retains an original sequential ETL (512 MB
per-capture ceiling). Live display examples are bounded separately; archived
ETL pages read original events without the live sampling budget. Event/buffer
loss, decode errors, display omissions and collection gaps are different
counters. Normal stop records final ETL SHA-256, bytes and counters. Privileged
kernel capture is user-started, never auto-elevated. Windows ABI, shutdown,
forced-exit recovery and provider coverage must be tested. Continuous ETL
rotation/background capture remains required as F135; it is not implemented
or claimed gapless by this increment.

D027 — Continuing per-event journal with bounded ordinary disk-sync batching
Every event remains appended individually and reaches the OS immediately. Ordinary
rows sync at the next one-second timer tick under normal scheduling, and at close.
CAPI2, label-version and scan commits sync synchronously before success/cursor
advancement. This replaces expensive disk barriers on every ordinary observation
without replacing logs with snapshots. Source-record loss on scheduling delays or
power failure is still possible and is not claimed away. Measured first complete
GUI inventory improved from 161 seconds (x64) and a 180-second timeout (ARM64) to
29/34 seconds on the later hosted run. Native source access errors remain visible.

D028 — Checkpoint read/replacement race, 2026-10-07 UTC

being atomically replaced concurrently with a read. Serialize reads under the
same archive gate used by replacement writes. A 100-write/1000-read regression
requires complete values, the final replacement and no retained storage errors.

D030 — Two incident classes, two different answers
Key compromise (eMudhra, INC-2026-10-B) is answered by a block list: hashes
are published, and a block on the key covers every certificate carrying it.
Registry/DNS hijack (ccTLD, INC-2026-10-A) is NOT answered by any country,
owner or root block: the rogue certificates chain to ordinary trusted CAs.
It needs S5 CT issuance data compared with the encountered certificate and
the "issuing CA changed for this domain" flag. The S5 incident CSV gains a
"class" column: key_compromise | dns_hijack | misissuance | other.

D031 — Block on SPKI SHA-256 as well as certificate SHA-256
Chrome blocked eMudhra by SPKI hash, which also caught the Sectigo
cross-signs: 8 keys, 16 certificates. S2 group block and the S5 incident
match carry both keys. A certificate-hash match proves that exact
certificate; an SPKI match proves the same public key under any issuer. The
dry run lists every certificate in every store that shares the SPKI, so the
cross-signed copy cannot be missed. Microsoft's own Disallowed list entries
are certificate based [to test]; kisib reports what Windows actually holds.

D032 — Country tags stack across one chain
eMudhra shows one chain carrying NL or US (subject C=), IN (emSign root,
CA owner) and GB (AAA Certificate Services cross-sign). The S3 CSV join on a
certificate's own C= alone would tag these intermediates NL or US and never
IN. S3 therefore offers per-certificate C=, issuer C=, CA owner country and
"any certificate in the returned chain" as separate, selectable tag sources;
tags from each source stack and each shows where it came from. No country is
hardcoded; every classification still comes from the CSV files.
Note on the user's draft CSV: NL is marked 👑, so a monarchy block by subject
C= would catch eMudhra BV's NL intermediates, and an India block by subject
C= would catch none of them. The dry run must show which tag source matched.

D052 Speed and crashes (user, 2026-10-26: "really slow, crashing on desktop and laptop, 4k+ disallowed").
Causes found: every store write asked the store for its whole list per certificate (O(n^2) with 4k
entries; the start-up re-apply froze kisib), the blocked list file was rewritten once per certificate,
"who is blocked" was recomputed by walking every certificate in about a dozen places and once per live-map
box, and everything rescanned and redrew every 60 seconds on the window thread. Now: stores are read once
per operation (OwnStore, registry part only), list files are written once per batch, lookups are built once
per scan (Snapshot.Blocked / BySha1 / SameKey), parsed certificates are cached per run, groups, rules, paths
and leaks are built in the scan worker, rescans come from registry change notifications on the certificate
store keys (plus 10 minutes) and skip redrawing when the stores and kisib's files are unchanged. The live map
keeps the last hour and redraws only on change. Errors go to CRASH LOG.txt instead of closing kisib.

D063 "Microsoft's list doesn't have Apple Root CA" was wrong (user screenshot, 2026-10-26). The fetch only trusted
a fresh certutil -generateSSTFromWU list and matched by SHA-1; a short list (firewall cutting certutil off) or a
SHA-1 that wasn't the self-signed copy made it say no. Now the deciding list is Windows' own authroot.stl,
read from HKLM\SOFTWARE\Microsoft\SystemCertificates\AuthRoot\AutoUpdate\EncodedCtl (admin-only; entries
are SEQUENCE { OCTET STRING sha1, attributes }, parsed by a small DER walker). Candidates come from kisib's
records matching the request or the root's name; a candidate is added only if that list names its SHA-1, and
its bytes come from kisib's lists, Windows Update's own <SHA-1>.crt download or certutil, checked by SHA-1.
Without a stored list it falls back to certutil and says why (and if the automatic root download is off).
--do status shows the list's size and sync date.
