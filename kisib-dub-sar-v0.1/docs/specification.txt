Order

First open the explorer and enumerate the actual machine, with durable logging and public-certificate retention active from the first scan. No backup, certificate import, or certificate-store write code belongs in this stage. Chain, CTL, complete CCADB catalog ingestion, CSV annotation, and owner grids follow the machine enumeration gate. The complete CA catalog is the required baseline; software-release evidence supplements it. Preparing source does not mean passing Windows verification.

Tag meanings

documented = the named behavior or term has a primary source.
to test = the implementation, machine behavior, mapping, or report header is unverified.
Documentation is not a claim that the program has passed Windows testing.
Custom geo, alignment, and flags are explicitly user-defined. Microsoft has no certificate term for political alignment or local organization flags. The source register gives the Microsoft API for underlying certificate data or presentation, and identifies external labels as external.

1. Real tree and certificate occurrences

System store location > system store > physical store.
System stores are native logical collections. Show the physical siblings actually returned by CertEnumPhysicalStore, including predefined and additionally registered siblings. Read the logical collection separately; its list is not fabricated by unioning physical-store results.

The documented baseline is:

Root: .Default .AuthRoot .GroupPolicy .Enterprise .SmartCard
CA and Trust: .Default .GroupPolicy .Enterprise
MY: .Default
CURRENT_USER: HKCU\Software\Microsoft\SystemCertificates

CA and Trust: .Default .GroupPolicy .LocalMachine

Also query CURRENT_SERVICE, SERVICES, USERS, and LOCAL_MACHINE_ENTERPRISE. Services use the named service registry scope; USERS uses the SID scope. A desktop application cannot invent a current service identity. User hives that Windows does not expose remain outside this read-only scan. The exact enterprise cache registry mapping is to test.

List columns: Subject, Issuer, Not before, Not after, Found in, Key algorithm, Key size (bits), Signature algorithm, SPKI SHA-256, Weak tier, SHA-1 collision, Key reuse. These added columns were explicitly requested. No further columns are inferred.
Found in contains every observed physical-store occurrence of identical certificate DER across the scanned scopes. SHA-256 indexes the DER; equal hashes are checked against full DER before merging. Provider aliases such as .LocalMachine remain visible. This is evidence of enumeration through those physical siblings, not a guessed backing registry path.

Empty, unavailable, denied, partially decoded, and unresolved results stay distinguishable. Native errors appear in the tree/details and activity log. A certificate returned by a collection but not found in an accessible physical sibling stays visible with unresolved provenance.

1a. Key metadata and inventory signals

Key algorithm uses PublicKey.Oid, with the friendly name and the numeric OID shown [documented]. Signature algorithm uses X509Certificate2.SignatureAlgorithm, with the friendly name and OID [documented]. Neither depends on a guessed issuer.

Key size is in bits [to test]. RSA size is the actual positive modulus bit length read from the public SubjectPublicKeyInfo; do not round 2047 up to 2048. EC and DSA use the decoded public key's AsymmetricAlgorithm.KeySize. Unsupported algorithms, provider errors, and failed decoding stay unavailable.

SPKI SHA-256 [to test] hashes the complete original DER SubjectPublicKeyInfo sequence, including its algorithm identifier, parameters, and public-key bit string. It is not the certificate SHA-256 or a hash of raw key bits. Preserve original bytes instead of re-encoding. CERT_PUBLIC_KEY_INFO is the Microsoft data term; exact DER slicing is application code requiring verification.
The metadata reader rejects truncated/noncanonical envelopes and differing inner/outer signature AlgorithmIdentifier encodings instead of mixing an OID from one field with parameters from another. These structural checks do not verify the certificate signature or replace Windows chain policy.

Weak tier [to test] applies the requested local rule: RSA public key under 2048 bits OR certificate signature digest MD5 OR certificate signature digest SHA-1. Show every matched reason. The public-key algorithm and signature algorithm are assessed separately. RSA-PSS requires its signature parameters; a valid parameter sequence with an omitted hashAlgorithm uses the specified SHA-1 default. Missing or unclassified parameters/digest produce an incomplete assessment. The rule is user-defined, not a Microsoft trust or Root Program compliance verdict. No listed criterion is not a claim of secure cryptography.

SHA-1 collision [to test]: across all certificate records in the observed snapshot, an identical full-certificate SHA-1 and more than one distinct full-certificate SHA-256 marks every affected row's collision cell red. Selection must not conceal that cell. Details show peer Subject, SHA-256, and observed physical sources. Never merge by SHA-1. Repeated occurrences of identical DER do not cause this signal.

Key reuse [to test]: identical SPKI SHA-256 appearing under more than one distinct full displayed Subject DN (ordinal comparison) marks all affected records. Compare the complete subject, not only CN. Reissuance with the same subject and store duplicates do not trigger it. Key reuse is an observation, not a compromise verdict. Details show the differently named peers. A folder selection does not narrow either inventory check. Missing or inaccessible stores limit the observed inventory; a no-match cell does not establish worldwide uniqueness.

2. Windows chain view after the gate

Call CertGetCertificateChain for the selected certificate. Render CERT_CHAIN_CONTEXT and its ordered CERT_SIMPLE_CHAIN element arrays from left to right. Draw every simple chain actually returned, and preserve which chain context owns it. Alternative lower-quality contexts require CERT_CHAIN_RETURN_LOWER_QUALITY_CONTEXTS; preserve their identity rather than flattening them into one guessed tree. This API does not promise every possible chain.

Each hop links consecutive elements returned by Windows. Issuer name, Authority Key Identifier, Subject Key Identifier, signatures, and Windows chain rules identify/validate candidate parents; a matching name or identifier alone is not proof of a parent. Certificate hashes are lookup keys, not parent edges.

Cards: CN when present; SHA-256 and SHA-1 with Copy; observed Found in occurrences; the element's CERT_TRUST_STATUS; Microsoft and Mozilla program-list results; C= when present; local tag and flag values. Show partial-chain endings explicitly. An issuer returned by Windows without an inventory match says not found in enumerated stores. Do not invent an origin. Windows element trust, chain policy results, and program inclusion are separate facts.

Default chain construction must be cache-only and disable automatic root update/AIA retrieval so an inspection cannot silently populate persistent stores. Proposed flags include CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL, CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE, and CERT_CHAIN_DISABLE_AIA. Revocation checks need their own cache-only flag and explicit coverage result. These effects require a Windows before/after test before the read-only claim extends to chain building.

Microsoft term: CertGetCertificateChain; CERT_CHAIN_CONTEXT; CERT_SIMPLE_CHAIN; CERT_CHAIN_ELEMENT; CERT_TRUST_STATUS.
https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain
Tag: documented API; chain rendering and read-only side effects: to test.

3. Hash strips after the gate

Under each chain card, show key > list > value. Keep all hit, miss, unloaded, invalid, and unavailable results visible. Include the list's date and provenance; an unknown publisher date remains unknown.

SHA-1 > Microsoft trusted CTL > membership and decoded usage/constraints.
SHA-1 > Microsoft untrusted CTL > disallowed membership.
SHA-256 > CCADB All Certificate Information CSV > CA Owner, Microsoft status, Mozilla status, using the actual source headers.

A CTL hit does not by itself establish that this certificate is valid for this purpose on this machine. A miss does not by itself establish trust or distrust. Logging and read-only boundary

View > History log and Certificate > Certificate history read durable UTC journals across scans and launches. Each observed certificate occurrence and EKU observation is recorded; public DER is retained immediately. Immutable inventory/index objects preserve prior metadata and source evidence, with identical contents deduplicated. A 60-second non-overlapping scan while the explorer runs appends observations instead of replacing history. Per-source successful baselines support additions/removals/usage changes; inaccessible, missing or canceled sources remain unknown. Storage faults stay visible. See docs/archive-requirements.txt and F102-F111 for source, format, recovery and coverage. No private keys are opened or exported. The explorer opens existing stores using CERT_STORE_READONLY_FLAG and CERT_STORE_OPEN_EXISTING_FLAG. CERT_STORE_ENUM_ARCHIVED_FLAG includes archived certificates. No OS store mutation, registry editing, or certificate auto-download API is called. Supported CAPI2 replay/live collection and optional owned ETW syscall capture now have prepared source; complete application/verifier coverage remains required, with source gaps explicit.

are durable before replay bookmarks advance. Missing/disabled/access-denied

retains full sequential ETLs within the 512 MB per-capture ceiling. Display
examples, source event/buffer loss and decoder errors are distinct. Raw
addresses and NTSTATUS are retained without guessed symbols, pairing or
certificate purpose. Original ETL paging has no live sampling budget.
